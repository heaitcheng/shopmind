| 轮次 | 改动 | 订单号 | 意图 | 缺失项召回 |
|---|---|---|---|---|
| 1 | 初版 prompt | 94.4% | 88.9% | 44.4% |

### 拒绝或纠偏

- **没有自行给 429 写应用层重试**：先用 SDK 自带的 `max_retries`，只在评估脚本（批处理、可以等）里加重退避。服务端不为限流引入额外代码路径。
- **没有为了指标好看改评估口径**：两轮 prompt 调优后指标一升一降（订单号 94.4%→86.7%），如实保留。最后一条「意图 90%」的两处错判，复核后判定是我的标注有歧义，不是模型错，也照实写进 spec，没有改成正确。
- **没有听用户口头结论就直接改代码**：用户说「填了还是不行」，先查 `.env` 实际内容（49 位、纯 ASCII、无空格，key 没问题），再定位到是进程内 `lru_cache` 缓存了启动时的旧配置。**如果顺着"key 有问题"去改，就会改错地方。**
- **没有用 `glm-4.7-flashx`**：文档没给准确 model id，探针测试两台都返回 `HTTP 000`/`429`，而 `glm-4.5-airx` 实测可通，按证据选后者，不按价格表想当然。

### 翻车与返工

1. `get_settings()` 用了 `lru_cache`，改完 `.env` 服务端读不到，表现成「填了 key 还是报占位符」。改成不缓存配置、只按配置组合缓存 LLM 实例，`LLM_MODEL`/`LLM_API_KEY` 改完下一次请求即生效。
2. `.env` 里占位符是中文「在这里粘贴你的智谱APIKey」，被当成真 key 拼进 `Authorization` 头，SDK 抛 `'ascii' codec can't encode characters`。这个错完全指不到 key 上。加了 `_check_api_key` 前置校验，返回人话 503。
3. 依赖注入层抛 `RuntimeError`，FastAPI 直接吐裸 500。改成 `HTTPException(503, detail=...)`，前端也补了从 JSON body 读 `detail`。
4. `/api/chat/reset` 复用了 `ChatRequest`（`message` 必填），而页面清空按钮只发 `session_id`，实测 422。补 `ResetRequest` 并加两条回归测试。
5. 模型在 `order_id` 为空时返回**字符串 `"null"`** 而不是 `null`，污染一切判空逻辑。加 `_clean_text` 归一化，覆盖 `"null"/"none"/"n/a"/""` 等写法。
6. 免费档 `glm-4.7-flash` 限流极凶：20 条连续请求约 1/4 触发 429，SDK 的两次退避也压不住。评估脚本因此加了 8s/20s/40s 长退避。
7. 一次全量测试出现 6 个 `PermissionError: [WinError 10013]`，与正在重启的 uvicorn 抢端口有关，重跑即恢复。属环境瞬时问题，不是代码缺陷。

## 阶段 9 · 修「第二轮开头多一行空白」（2026-10-31）

### 用户关键原话

- 「从第二条消息开始，每次都会先输出一个空白行再输出回答，这个有问题吧」

### 关键产出

- 复现取到确切证据：第一轮首个 chunk 是 `'请问'`，第二轮首个 chunk 是 `'\n'`。
- **根因**：历史里有 assistant 消息时，GLM 会在新回答前吐一个换行当段落分隔。这是模型输出习惯，不是传输层丢字节，`_clean_text` 那类字段归一化管不到这条路径。
- 修在服务端流式入口：`ChatService.stream` 加 `pending_leading` 标志，在收到第一个非空白 chunk 之前吞掉空白；正文中间的空行原样保留。
- 新增 4 条测试：首 token 不吃前导换行、中间空行要保留、连续空白首块不产生空 token、真实两轮端到端验证。

### 拒绝或纠偏

- **没修在前端**：前端 `trim()` 也能让用户看不到空白行，但流式过程中会先渲染一行空白再回退，视觉上抖一下。修在源头更干净。
- **没有全局 strip**：只吃前导空白。整段 `strip()` 会把正文里的分段空行一起吃掉，客服回答经常分段（「分两步：第一…第二…」），那是正常排版。

### 翻车与返工

1. 验证时用 `curl ... | head -2` 只看首帧，结果第二轮返回「我没有记忆功能」——一度以为上下文丢了。实际是 `head` 提前关闭管道导致连接被取消，而历史只在整轮成功后落盘，所以第一轮根本没存。**测量手法本身制造了假 bug。** 改成完整消费流后即正常。
2. 这个插曲顺带确认了一条真实行为：**客户端中途断开时，本轮对话不会落盘**。设计上是对的（半截回答不该进历史），但意味着用户点「停止」或关页面，刚说的话不会被记住。已记在这里，UI 上暂不处理。
3. 用 `grep '"content":"'` 取 JSON 字段失败——实际序列化是 `"content": "` 带空格。匹配式写死格式容易踩这种坑。

## 阶段 10 · 修「没有上下文」与「Connection error」（2026-10-31）

### 用户关键原话

- 「你好 → 您好，请问有什么售后问题需要帮助吗？／我刚刚在说什么 → 您没有说任何内容／订单号S202605720832我要退款 → 出错了：Connection error.」
- 「存在两个问题：第一没有上下文，第二报错出错了：Connection error.」

### 关键产出

两个现象是三层原因叠加，逐层拆开后分别修：

**第 1 层：Connection error = 服务进程吃到了过期代理**
- 证据：shell 的 `https_proxy` 端口从 64018 变成了 57971，而服务进程继承的是启动时的旧值，端口已死。
- 决定性实验：同一个死代理环境下，`ChatOpenAI` 不传 `http_client` → `OpenAIConnectionError: Connection error.`；传 `trust_env=False` 的 client → 成功。
- 修法：`app/llm.py` 新增 `_http_clients()`，默认 `trust_env=False`，需要走代理时用 `.env` 的 `LLM_PROXY` 显式指定。

**第 2 层：首条失败 → 之后永久失忆**
- 前端只在 `done` 事件里拿 `session_id`，第一条请求失败就没有 id，之后每条消息都是全新会话。
- 修法：前端首次发送时自己生成 `session_id`（`crypto.randomUUID`，带降级），后续一直复用。后端本来就接受外部传入的 id，无需改动。

**第 3 层：上下文在，但模型拒绝回答回顾类问题**
- 证据：会话里先给「我叫何新成，订单号 SO20261029001」，再问「我叫什么名字」→ 答「您是何新成先生」，说明历史是好的。
- 但问「我刚刚说了什么」→ 答「您没有提供具体问题」，把话题拐回售后。模型在死守客服人设。
- 修法：system prompt 加第 7 条，明确要求复述上文、禁止说「没有记录」、禁止反问。

### 拒绝或纠偏

- **没有停在第一个假设上**：最初只归因于「首条失败导致 session 丢失」，但同一 session_id 连发两轮仍然丢上下文，说明还有第二层。继续用「问名字」这种可辨识信息做对照实验，才分离出「历史正常、模型不认账」这第三层。
- **没信 langchain 的警告文案**：它提示「已禁用代理自动检测」，但实测默认行为照样吃环境代理。以实验为准，不以日志文案为准。
- **没有把 `tail` 取数错误当成服务故障**：中途两次看到"空响应"，都是取行方式取到了 SSE 末尾空行，不是接口真的没返回。

### 翻车与返工

1. 一开始设计验证脚本时连续犯了三次同类错误：`curl | head -2` 提前断流导致历史不落盘（误判为上下文丢失）、`grep '"content":"'` 漏了冒号后的空格、`tail -1` 取到 SSE 尾部空行。**三次都是测量手法制造了假 bug**，教训是验证命令本身要先用已知输出去校准。
2. 试图用"死代理环境启动 uvicorn"来验证修复，结果启动阶段就崩在 `PermissionError: [WinError 10013]`（socketpair 被拦）。改用直接调模型的方式验证，效果等价且不受服务启动影响。
3. `httpx` 代理配置的断言一开始写成 `_pool._proxy_url`，该版本没有这个属性；`_pool._proxy` 也存在但为 `None`。最终改用 `len(client._mounts)` 判断是否挂了代理，稳定。
4. langchain-openai 传自定义 `http_client` 时会打印一条关于 `http_socket_options` 的警告，属噪音，不影响功能，未处理。
