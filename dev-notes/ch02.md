## 阶段 1 · brainstorm 定稿（2026-10-31）

### 用户关键原话

- 「我要用 Superpowers 模式给现有的客服系统装上查数据的能力，用 Function Calling 让模型自己决定调什么工具——工具链要长在客服聊天本身，用户在聊天页问一句就能触发。」
- 「本章不做：多轮自动循环的 Agent Loop、向量检索、RAG」
- 「只做单轮调用：模型调一次工具就收敛」
- 「确认关键词查表查不出来——这个漏召回是预期结果，记下来留给下一步升级」
- 「技术选型定死，走不通停下问我，不要自行换方案」
- 「我听不懂，重新详细问一个这个问题并且讲解每个选项」／「听不懂先解释」

### 关键产出

- `docs/ch02-spec.md` —— 设计定稿。含分层目录、四张表结构、五个工具的参数与实现、工具基础设施的四道关（校验/超时/重试/错误封装）、单轮编排流程、SSE 新增 `tool` 帧协议、落库策略、测试策略、已知限制。
- 已核对 API 事实（Context7 + 本地实测）：
  - `@tool` 从类型注解自动生成 args_schema（`order_id: int` → `integer` 且必填）
  - 流式下工具调用是 `tool_call_chunks` 分片，必须 `gathered + chunk` 累积后才能拿到完整 `tool_calls`
  - 工具实例支持 `handle_tool_error` / `handle_validation_error`，不必自己包 try
  - SQLAlchemy 2.1.6 异步写法、aiomysql 0.3.2 纯 Python 可装

### 拒绝或纠偏

- **用户两题听不懂，我重写问题而不是硬推**：第一版问了「测试怎么处理 MySQL 依赖」「同步还是异步」，用了「方言差异」「阻塞事件循环」这类词。用户回「我听不懂，重新详细问一个」。返工后改成分场景讲后果（忘了开 Docker 会分不清是代码错还是环境错、同步驱动会把整个事件循环卡住），用户才作答。
- **create_ticket 的 conversation_id 不能交给模型**：用户的需求写的是「写入 tickets 表」，但没说明 conversation_id 从哪来。模型编不出真实会话 id，写进去就是脏数据。改成执行器用闭包注入，模型只填 description 和 ticket_type。
- **假数据必须确定性**：用户原本只说「随机生成数据返回」。但验收标准要演示「订单 1001 的物流到哪了」，真随机会导致同一个问题两次答案不同，演示飘、测试没法断言。改成 `random.Random(order_id)` 播种，用户确认。
- **没扩大范围**：不做 Alembic 迁移、不做 Agent Loop、不做 RAG。用户没要求的都没加。
- **明确保留 ch01 的进程内 SessionStore**：数据库只做记录，不参与上下文组装。避免把「上下文裁剪」和「持久化」两件事混在一起。

### 翻车与返工

1. **Docker daemon 没起**：`docker` 命令在，但 `dockerDesktopLinuxEngine` 管道不存在，`docker info` 直接报错。需要用户手动启动 Docker Desktop（这台机器冷启动很慢）。这是开工前的硬前置，不是代码问题。
2. **第一次的问题卡片术语过重**，四个问题里两个被回「听不懂」。教训：问选择题时，选项描述要写「选了这个会发生什么」，而不是「这个方案的技术特性叫什么」。
3. `bind_tools` 的签名一开始用 `import langchain_openai; langchain_openai.openai.ChatOpenAI` 取，报 `module has no attribute 'openai'`。正确路径是 `from langchain_openai import ChatOpenAI`。

### 翻车与返工

1. **问题卡片第二次被回「听不懂」**：问「全面分层 vs 只加两个包」时用了「对称性」「半拉子」这类抽象说法，用户要求详细讲。改成先画 before/after 目录树、再讲「选了这个会发生什么」，才通过。同一个坑在本次会话里踩了第二次（第一次是问测试连库），教训是**选择题要讲后果，不要讲术语**。
2. **`STATIC_DIR` 差点埋雷**：`Path(__file__).parent.parent / "static"` 在 `app/main.py` 里正好指向仓库根，文件一搬到 `app/api/routes.py` 就会变成 `app/static`，首页直接 404。这个坑在派活前就预判到并写进子代理 prompt，实测改为 `parents[2]` 后 `GET /` 返回 200。
3. **FastAPI 0.162 的 `include_router` 不再摊平路由**：`app.routes` 里只多一个 `_IncludedRouter` 惰性节点，没有 `.path` 属性，导致我给子代理的验证命令输出为空。子代理没有为了迁就验证命令去改装配方式，而是改用递归展开 + `app.openapi()["paths"]` 复核，判断正确。
4. 子代理报告称路由文件与原 `main.py` "除 4 处外逐字一致"，我自己用 `diff` 复核，确认差异只有：import 行、`STATIC_DIR`、`app→router`、五个装饰器。**没有只信汇报。**

### 拒绝或纠偏

- **不接受「用 SQLite 兜底」**：子代理遇到 aiomysql 认证问题时列出两条绕法，其中一条是改用 SQLite。用户已明确要求测试连真 MySQL，直接排除，改补 `cryptography` 依赖。
- **不接受「静默降级」**：测试库隔离时明确要求 `TEST_DATABASE_URL` 为空就 `pytest.exit` 中止，**不许偷偷回退去连演示库**——静默降级正是「跑测试清空演示数据」这个 bug 的成因。
- **子代理的验证脚本判据写错，我没跟着错**：它用 `"collation" in ddl.lower()` 判断排序规则，永远为 False（MySQL DDL 里是 `COLLATE=...`）。我自己改用 `"COLLATE=utf8mb4_unicode_ci" in ddl` 复核，四张表全部通过。
- **计划第二次变更**：B2（15 行）与 B3 合并执行，理由和 A1 一样，已写进 `docs/ch02-plan.md`。

### 翻车与返工

1. **`mysql:8` 实际是 8.4.13**，不是 8.0.x。8.4 移除了 `mysql_native_password` 默认支持，账号改用 `caching_sha2_password`，导致 aiomysql 明文连接报 `'cryptography' package is required`。
2. **绕路也失败**：aiomysql + TLS 在 Windows Proactor 事件循环下报 `OSError [WinError 87]`（socket dup + TLS 升级的系统限制），只有换 Selector 循环才行——那会让服务端启动也得配合改 loop policy，明显更脏。最终选装 `cryptography`，一行依赖解决。
3. **测试把演示数据清空了**（真实缺陷，不是预期行为）：测试夹具连的是演示库 `shopmind`，跑一次 `pytest`，`faq` 从 17 条变 0 条。是子代理在汇报里主动提的。修法：建独立 `shopmind_test` 库，`TEST_DATABASE_URL` 指向它，并补一条防回归测试断言 `SELECT DATABASE()` 等于 `shopmind_test`。
4. **事件循环跨 loop 复用连接**：session 级 engine 的连接池跨用例复用时抛 `Future attached to a different loop`。解法是给 `engine` / `db_session` 加 `loop_scope="session"`，测试文件加 `pytestmark = pytest.mark.asyncio(loop_scope="session")`，而不是引入 `NullPool` 或改全局 `pytest.ini`。
5. **测试与种子数据撞车**：跑出 `MultipleResultsFound`，因为库里已有 seed 的同名 FAQ，测试又插一条，`.one()` 查到两行。修法不是改断言，而是让 `db_session` 在 yield 前后各清一次表。
