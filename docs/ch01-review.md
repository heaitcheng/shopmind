## 一、当初没问的问题

### 1. 会话没有任何归属校验 —— Critical，但 ch01 本地运行可接受

**证据**：`app/service.py:58` 的 `sid = session_id or self._new_id()` 直接用客户端传来的字符串；`app/main.py:97` 的 `store.clear(req.session_id)` 同理。

**后果**：任何人拿到或猜到 `session_id`，就能读该会话的上下文、往里续写、把它清空。uuid4 hex 不好猜，但它会出现在浏览器内存、curl 命令、日志里，**不是安全边界**。

**为什么 ch01 不修**：无鉴权、无多用户、只跑 localhost。

**什么时候必须修**：一旦部署到公网，或者出现第二个使用者。修法不是加登录，而是把会话绑到一个不可伪造的令牌上（服务端签发、客户端只持有不可解析的引用）。

### 2. 对话链路和抽取链路是两条平行线 —— High

**证据**：`ChatService.stream` 和 `ChatService.extract` 互不调用。聊天页面只打 `/api/chat/stream`；`/api/chat/extract` 除了 curl 和评估脚本，没有任何生产调用方。

**后果**：验收标准 3 确实过了，但它是**并列的第二个功能**，不是「客服能力的一部分」。`missing_fields` 这个字段目前一个消费方都没有。

**诚实说法**：如果面试被问「抽取出来的结果怎么用」，章节内的答案只能是「下一章用」。这是为 ch02 留的钩子，但在 ch01 交付物里，它是死字段。

### 3. 多 worker 会静默丢上下文 —— High

**证据**：`app/main.py:19` 的 `store = SessionStore()` 是模块级全局 + 进程内 dict。

**后果**：`uvicorn --workers 4` 时，同一个 `session_id` 打到不同 worker 就丢历史。**不报错，只是模型「忘了」**——这类 bug 最难查，因为它表现为「AI 变笨」而不是「服务出错」。

**现状**：README 只写了「只跑单 worker」，没有量化。4 worker 下会话命中率理论值 25%。

### 4. 1500 的 token 预算没有依据 —— Medium，但有实测

实测（`count_tokens`，cl100k_base）：

| 项 | 实测值 |
|---|---|
| system prompt | 253 tokens |
| 抽取指令 | 325 tokens |
| 一轮对话（用户+客服） | 约 58 tokens |
| 1500 预算可容纳轮数 | 约 21.5 轮 |
| 实际上下文上限 | 253 + 1500 = 1753 tokens |
| 占 glm-4.5-airx 128K 窗口 | **1.37%** |

**结论**：这个数字不是按窗口推的，是拍的。它用 98.6% 的窗口换「省钱 + 低延迟」，对客服场景（很少聊满 20 轮）算合理，但应该清楚自己在放弃什么。正确做法是按「业务上最长的对话轮数 × 平均 token」反推，而不是拍一个整数。

**另一个细节**：`include_system=False`，所以 system prompt 不占这 1500 的预算，是额外加的。看代码容易误以为 1500 是全部上下文。

### 5. 评估集的方法论缺陷 —— High，直接影响可信度

- 20 条样本由我一人编写，单一场景（售后退换货），没有覆盖多商品、多订单、带凭证等分支
- **没有 held-out 集**：调 prompt 用的就是这 20 条，最后报的也是这 20 条，等于在训练集上评估
- 两条「意图错判」我判定为标注歧义——**这个判定没有第二个人复核，等于自己给自己判分**
- 只测字段 exact match，不测「该拒绝时是否拒绝」（例如用户问物流，模型不该硬抽售后字段）
- 完全没测客服话术质量，所以「Prompt 管理」这条需求的验收其实是不充分的

### 6. 流式中途失败的处理是半成品 —— Medium

**证据**：`static/index.html:315` 保留已累积的 `answer` 并把气泡标红。

**问题**：用户看到的是一段被标红的半截话，但没有任何文字说明「这句没说完」。模型说到一半断了，和说完了，肉眼分不出。

**缺失**：没有断线重连，也没有断点续传（SSE 天然不支持）。至少该在没收到 `done` 时明确判定为异常并提示重试。

## 二、「看起来对、其实是补丁」的三处

### 1. `_clean_text` 归一化 `"null"`

根因是模型在 `function_calling` 下把空值写成字符串。补丁只覆盖了 `null/none/nil/n/a/-`，模型要是写成 `"（空）"` 就又漏。更彻底的路子是切 `json_schema` method（智谱未必支持）或在 schema 里显式声明可空。

### 2. `max_retries=2` 挡 429

SDK 的退避是秒级，智谱免费档的限流是分钟级，所以 2 次根本不够——实测 20 条里挂 5 条。真解是队列 + 令牌桶，但那超出 ch01 边界，所以这次是靠换付费档绕过去的。**换档解决了现象，没解决问题。**

### 3. `_check_api_key` 校验

根因是 `.env.example` 里把 key 写成了中文占位符，被当成真值用。更干净的做法是 `.env.example` 里 key 留空，靠 `min_length` 卡住，而不是事后识别「这看起来像占位符」。现在的实现是在猜用户意图。

## 三、拍脑袋的配置清单

| 项 | 现值 | 依据 | 该怎么定 |
|---|---|---|---|
| `HISTORY_MAX_TOKENS` | 1500 | 拍的 | 按最长对话轮数 × 平均 token 反推 |
| `LLM_TEMPERATURE` | 0.7 | 通用默认 | 对话 0.7 可以，**抽取该降到 0～0.2**，现在两者共用一个值 |
| `LLM_MAX_RETRIES` | 2 | SDK 默认 | 按上游限流特征定，免费档明显不够 |
| 评估集规模 | 20 | 随手 | 至少 50，并留 20 条 held-out |
| 会话过期 | 无 | 忘了 | 30 分钟 TTL，否则内存无界增长 |
| `LLM_TIMEOUT` | 60s | 拍的 | 实测单轮首 token 常在 2-5s，60s 偏保守但也无害 |

## 四、如果重做，改动优先级

**P0 不做会出事**
1. 会话归属校验（哪怕只是个 HMAC 签名）
2. 单 worker 限制写进启动脚本，或换外部存储

**P1 影响可信度**
3. 评估集拆 train / held-out，50 条起
4. 补「该拒绝时是否拒绝」的负例——这是客服最该测的能力
5. 抽取单独用低温，别和对话共用 temperature

**P2 体验**
6. 流中断时显式提示「回复中断」
7. 页面渲染 Markdown（现在 `**加粗**` 原样显示）

**P3 工程**
8. 加日志与 token 用量统计（现在**一行日志都没有**，线上出问题纯靠猜）
9. 会话 TTL 淘汰

## 五、给 ch02 的前置条件

1. **先定工具调用的失败语义，再写代码。** 模型调错工具、参数瞎编、该转人工时没转——这三件事要各自有明确策略，否则会边写边改。
2. **抽取结果必须接进对话链路。** 不进链路，`missing_fields` 就永远是死字段，ch01 的这个接口也就永远是个演示。
3. **评估集先扩到 50 条并留 held-out。** 工具调用比抽取更难验证，靠 20 条样本支撑不住结论。
4. **温度拆分**：抽取 0～0.2，对话 0.7。
